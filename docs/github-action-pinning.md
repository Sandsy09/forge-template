# GitHub Action pinning policy

This is the canonical living policy for GitHub Actions workflow references
owned or generated by `forge-template`. [ADR
0022](adr/0022-pin-github-actions-by-full-commit-sha.md) records why Forge
adopted full commit SHAs and updater-readable release comments.

The policy applies to this repository's workflows, the current generated
GitHub Actions workflow, and future GitHub platform contributions. It does not
make GitHub Actions a provider-neutral Foundation requirement or govern
`create-forge`'s repository-local automation.

## Immutable remote references

Every repository-based remote action or reusable workflow must use a full
40-character commit SHA. The exact upstream release tag must appear in a
same-line comment:

```yaml
- uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0
```

The SHA is the executable and authoritative reference. The comment is
reviewing and maintenance metadata: it makes the selected release legible to
people and lets supported dependency updaters discover the release line.
Branches, moving major tags, exact release tags, and shortened SHAs are not
accepted executable references. GitHub's
[secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use)
identifies a full-length commit SHA as the only immutable way to consume an
action.

The same rule applies to actions maintained under `actions/*`, other verified
publishers, private repositories, actions in repository subdirectories, and
remote reusable workflows. Publisher identity is useful review evidence but
does not make a mutable tag immutable.

Same-repository `./...` actions and reusable workflows are exempt because
their content is already bound to the calling repository commit. Forge does
not currently permit `docker://` actions: adopting one first requires a
separate digest-pinning and maintainable update path.

## Reviewing an update

Every action update requires a pull request and human review, including patch
and minor releases. An updater proposes a candidate; it does not establish
trust. The reviewer must:

1. identify the upstream release represented by the version comment;
2. review its release notes, source changes, permissions, inputs, outputs, and
   runner requirements;
3. independently confirm that the exact release tag resolves to the proposed
   commit SHA, dereferencing an annotated tag when necessary;
4. update the full SHA and version comment together; and
5. require the repository's complete CI contract to pass before merging.

Major action upgrades receive the same checks plus explicit compatibility
review of removed inputs, changed defaults, and runtime changes. They are not
folded into an unrelated pinning migration. A security response may advance
directly to a known-fixed release or disable the affected step, but must not
temporarily reintroduce a mutable reference.

Forge-provided dependency automation never auto-merges GitHub Action updates.
Repository owners may adopt stricter review, allowlisting, dependency-review,
or organisation policies after handoff.

## Maintenance paths

### forge-template repository

Root Dependabot configuration checks the `github-actions` ecosystem weekly on
Monday and opens reviewed `ci` pull requests. It is limited to five open pull
requests and applies the shared `type:chore` and `area:ci` labels. The policy
validator runs in `uv run poe check`, so a mutable or undocumented remote
reference cannot enter this repository unnoticed.

### Generated projects using Renovate

The generated Renovate configuration extends
`helpers:pinGitHubActionDigests`. Its GitHub Actions rule groups digest and
version updates, preserves full-SHA references, and explicitly disables
automerge. Renovate follows the exact release tag in the same-line comment;
see its
[GitHub Actions manager documentation](https://docs.renovatebot.com/modules/manager/github-actions/).

### Generated projects using Dependabot

The generated Dependabot configuration checks the `github-actions` ecosystem
weekly on Monday. Dependabot updates both a pinned SHA and its same-line
version documentation. It opens a pull request for review and does not merge
it. Projects must keep the exact release comment beside the reference so the
update remains associated with a release rather than an arbitrary branch
commit.

### Generated projects without automation

Selecting no dependency updater remains supported. The project owner manually
monitors upstream releases and security notices, follows the same review and
tag-to-SHA verification procedure, changes the SHA and comment together, and
runs the complete CI contract. Forge imposes no background service or
workstation state on that choice.

## Current pinned baseline

The initial migration deliberately preserves the existing action major lines:

| Action | Release | Commit SHA |
| --- | --- | --- |
| `actions/checkout` | `v4.4.0` | `11d5960a326750d5838078e36cf38b85af677262` |
| `astral-sh/setup-uv` | `v5.4.2` | `d4b2f3b6ecc6e67c4457f6d3e41ec42d3d0fcb86` |
| `actions/upload-artifact` | `v4.6.2` | `ea165f8d65b6e75b540449e92b4886f43607fa02` |

These versions describe the migration baseline, not a permanent ceiling.
Later updater pull requests may propose newer major lines through the review
process above.

## Generated-project and ownership boundary

The current monolithic Library scaffold always emits GitHub Actions CI, so its
workflow adopts this policy now. Future composition treats the workflow and
its pins as a GitHub platform contribution. Foundation continues to guarantee
a provider-neutral aggregate quality contract, not a particular automation
provider.

The validation helper is template-repository tooling. It does not enter the
generated Python package, add a runtime dependency, define a ProjectSpec field,
or change Copier's question or stored-answer schema. After handoff, a project
owner controls its independent repository and may replace the platform or
adopt a different policy.
